## Added 2026-08-14 — SEO fixes. Code only; ships with the next deploy

An audit of the live site found two things worth fixing immediately. Both are done.

### Product pages were telling Google they are the homepage

**The bug.** A path under `/{locale}/gallery/` was a known SPA route with *no* seo-manifest
entry, so `MapFallback` left the DEFAULT block in the shell — and that block carries
`<link rel="canonical" href="https://nvc-home4you.eu/">`. All 42 product URLs were therefore
declaring themselves duplicates of the homepage, while `sitemap-gallery.xml` dutifully
submitted every one of them. Verified before *and* after JavaScript: the client-side `<SEO>`
in `GalleryItemPage.jsx` did not override it either. A missing canonical is a guess; a wrong
one is an instruction.

**Why the fix is NOT in `generate-seo-manifest.mjs`.** That was the obvious move and it is
wrong: the generator runs at build time from the static route table, and products are
database rows staff rename through the admin panel. Baked tags would be stale the first time
somebody edits a title, and would need a redeploy to correct.

New `GallerySeoService` builds the tags **per request** instead, reading through
`GalleryService`'s existing 10-minute cache, so it costs a dictionary lookup rather than a
query per crawl. Products now get their own title, description (rich text stripped to a
155-char snippet on a word boundary), canonical, reciprocal bg/en/el/x-default hreflangs,
`og:type=product`, and **the product photo as `og:image`** — sharing a specific model used to
show the same generic image for every one of them.

**Bonus fix in the same branch:** a product-shaped URL naming a product that does not exist
now returns a real **404**. It used to be 200 + homepage metadata — a soft 404 for every
mistyped or retired product link ever shared.

### `GallerySlugs` — one copy of the slug rule, not two

`SitemapController` held the slug logic privately. The moment a second consumer needed it the
tempting move was to copy it, which is exactly how a sitemap starts advertising URLs the site
answers with a 404. Both now call `GallerySlugs`. **Verified: the refactor produced
byte-identical sitemap URLs** (42, diffed against the live sitemap).

One unavoidable copy remains in JS (`slugify()` in `src/gallery/galleryUtils.js`) because the
SPA routes on it client-side. `GallerySeoTests` pins the C# side to the same rule.

### The bare domain was a fourth homepage

`/` only redirected in the browser — `<Navigate>` in App.jsx, which no crawler runs. A
crawler got 200, the default shell, a self-canonical to `/`, and no hreflang: a word-for-word
duplicate of `/en`, outside the language cluster and competing with it. The manifest
generator now emits a `/` entry carrying the English home's tags with the canonical pointing
at `/en`. 52 routes, up from 51.

### Also fixed

- **Duplicate `LocalBusiness` schema.** Both `HomePage.jsx` and each `*HomeRoute.jsx`
  rendered `<LocalBusinessJSONLD>`, so every home page emitted `HomeAndConstructionBusiness`
  twice. Removed from the three route files; `HomePage`'s is kept because it passes the
  locale's real url/email/telephone — the route ones rendered it bare.
- **HSTS**, one year + subdomains. Written by hand rather than `app.UseHsts()`, which skips
  any request it considers insecure — behind App Service's proxy the inbound hop is plain
  http, so the header would silently never ship. Gated on the scheme `UseForwardedHeaders`
  has just corrected. Verified both ways: absent on plain http, present with
  `X-Forwarded-Proto: https`. **Not** `preload` — that is a one-way door and not ours to
  commit to from a code change.

### The body is no longer empty — prerendering, added the same day

`scripts/prerender.mjs` drives headless Chrome over the built, running app and saves what it
renders. **52/52 routes, 125,518 characters of crawlable text**, where every URL previously
served 0. Measured against production the same day:

| | live | after |
|---|---|---|
| `/bg` | 168 | 3,545 |
| `/el` | 186 | 4,024 |
| `/en/gallery` | 109 | 3,057 |
| `/en/modular-houses` | 116 | 1,864 |

Snapshots are served by `MapFallback` ahead of the shell, **to everyone** — serving a crawler
something a visitor does not get is cloaking, and the whole point is that the snapshot IS the
real page. Verified afterwards that React still hydrates and client-side routing still works.

**A snapshot is the rendered DOM, not a hand-written approximation.** That fidelity is the
reason for the headless browser rather than emitting HTML from the content files: an
approximation drifts from the real page, and drift here is the thing that gets a site
penalised.

**Three traps, all of which produced silent, successful-looking runs:**

1. **`networkidle2` is not "ready".** The first pass captured the Bulgarian gallery with 24
   card nodes where English and Greek had 108 — the grid's API call had not landed. Now waits
   for the rendered size to stop changing (`settle()`).
2. **The generator read back its own output.** The server serves snapshots, so prerendering
   against it re-saved the previous run: identical character counts, and a URL fixed in
   source stayed broken across two full rebuilds. The script now sends
   `X-Prerender-Bypass: 1`, which makes the server skip the snapshot and serve the live
   shell. **Do not remove that header.**
3. **The rendered DOM has two of every meta tag** — the server-injected block plus
   react-helmet's. Fine in a normal request (helmet's never reach the response), fatal in a
   snapshot, which freezes both. `dedupeHead()` keeps helmet's copy, because that is what a
   visitor ends up with. `<title>` is exempt: helmet retitles the existing element rather
   than adding a tagged one, so removing it as a "server tag" would ship pages with no title.

**New release step**, documented in `DEPLOY.md` §6b. Not automatic — it needs the app
running, which a publish does not have. `puppeteer` is a new devDependency.

### The prices page — `/bg/ceni`, `/en/prices`, `/el/times`

Targets `сглобяеми къщи цени`, the highest-intent query in the market and the one every
competitor ranks for with a price list. The gallery could not serve it: it shows a unit price
on fourteen separate pages, none of which mention that the unit still has to be assembled, so
a visitor reading €26,500 had no way to reach "€33,000 to move in".

**The two sides of the table are quoted on different bases** — this is the thing to remember:
catalogue house prices **already include VAT**, assembly is quoted **excluding** it.

| Model | House (inc VAT) | Assembly (ex VAT) | Assembly (inc VAT) | **Total inc VAT** |
|---|---|---|---|---|
| 37 m² | €14,000 | €700 | €840 | **€14,840** |
| 37 m² + roof & veranda | €16,700 | €1,300 | €1,560 | **€18,260** |
| 58 m² | €23,000 | €850 | €1,020 | **€24,020** |
| 58 m² + roof & veranda | €25,500 | €1,600 | €1,920 | **€27,420** |
| 73 m² | €26,500 | €1,000 | €1,200 | **€27,700** |
| 73 m² + roof & veranda | €28,000 | €1,900 | €2,280 | **€30,280** |

The first version of this page treated both sides as net and grossed up the sum, **charging
VAT twice on the house** and overstating every total by around €2,400. Corrected 2026-08-15.
`prices.test.js` now asserts specifically that the total minus gross assembly equals the
catalogue price untouched, so re-applying VAT to the house fails the suite rather than the
contract.

**Unit prices are imported from `boxConfiguratorCatalog.js`, never retyped** — a second copy
would drift on the next catalogue edition and the page would quote different numbers from the
configurator. Totals are computed, not stored, for the same reason `Purchase` has no
`LeftToPay` column. Assembly costs are the only figures originating in `prices.js`; confirmed
with the client 2026-08-14, along with the reading that the first "73 m²" in their message was
a typo for 37 m² (the roof premium then runs +600/+750/+900 with size).

Every column heading names its own VAT basis, because a single "excl./incl." pair over the
whole table would be wrong for half of it.

**The "not included" section is the point of the page, not a disclaimer.** Assembly covers
placement on a prepared base and turnkey finishing; it excludes the crane and the foundation,
and the page says so plainly and recommends Siana Burgas for ground screws. Every competitor
publishes a number that turns out to exclude something — saying which two things are extra
before anyone asks is what makes the rest of the table believable.

Wagons are handled with a pointer to the gallery, because their prices already include
assembly. Modular houses get a "no catalogue price, ask us" card, consistent with
`PurchaseCategories.WithGalleryModels` treating them as custom builds.

`prices.test.js` pins every figure, that VAT applies to the net rather than the unit price,
and that the numbers are identical in all three locales — a price that changed with the
language would be a legal problem, not a display bug.

### The prices page now covers the whole catalogue — priced FROM the gallery

Two sections, each with its cards and its own table directly beneath: 8 box houses, then 6
wagons. **The gallery is now the single price source** — the page's own price list was
deleted after the 73 m² incident, where the gallery and the configurator catalogue disagreed
by €1,000 for weeks and nothing could notice. `prices.js` adds only what the gallery does not
know: assembly costs, keyed by GALLERY ID so a title edit cannot silently drop one.

**The two sections do opposite arithmetic, and this is the thing to remember:**

| | Box houses | Wagons |
|---|---|---|
| Gallery price | house only, inc VAT | **total, inc VAT, assembly already inside** |
| Assembly | ADDED (€700–€3,000 net, shown ±VAT) | **SUBTRACTED OUT** (€1,000 gross, shown as "of which") |
| Confirmed | 2026-08-15 | 2026-08-15 |

Treating a wagon like a box house overstates it by €1,000; the table shapes differ (5 columns
vs 4) precisely so the reader never has to know which rule a row follows. Panorama 37 m²
assembly €1,900, two-storey 74 m² €3,000. All pinned in `prices.test.js`.

**A data-source trap, found the hard way.** The local app read Quickbase while production
read SQL — the flag is `DATA_SOURCE_GALLERY`, and EnvConfig's own comment wrongly said
`DATA_SOURCE_HOUSES` (now fixed). A corrected price showed live but not locally, and the
snapshots would have frozen the stale store's prices over the corrected data. The prerender
script now **compares the local catalogue against the live site and refuses to run on a
mismatch** (`PRERENDER_SKIP_DATA_CHECK=1` to override). DEPLOY.md §6b carries the flags.

## Added 2026-08-14 — customers, factories and purchases. DB migrated; app deploy still to run

Three new tables and two new admin screens, at `/admin/customers` and `/admin/factories`.

**The shape, and why it is three tables rather than two.** `Customer` holds only WHO someone
is; `Factory` is the supplier directory; **`Purchase` is the join, and every transactional
fact lives on it** — factory, category, model, deposit, final price, both invoices. A
customer and a factory never touch directly.

The obvious alternative was `FactoryId` plus the money as columns on `Customer`. It fails on
the second sale: a customer who takes a wagon in May and a modular house in July becomes
either one overwritten row or two customers sharing an ЕГН, and "how much has this client
spent with us?" stops being answerable. **Repeat purchases work on day one**, and when
billing moves off Quickbase it attaches to `Purchase` rather than fighting it.

| Decision | Why |
|---|---|
| **No `LeftToPay` column** | It is `FinalPrice - DepositPaid` and nothing else. Stored, it becomes a second copy of a fact that can disagree with the first — and the copy is the one people read. Computed in the DTO, recomputed live in the panel as the numbers are typed. |
| **Both money columns nullable, and they mean different things** | Null `FinalPrice` is "not agreed yet", a real state for weeks; null `DepositPaid` is "nothing has come in". Defaulting either to zero makes a deal with no agreed price report the deposit as an overpayment. |
| **`Eik` and `PersonalId` are separate columns** | An ЕИК identifies a company in a public register and is reasonable to search on. An ЕГН identifies a private individual and is the most sensitive value in the database. One column would mean every query touching company numbers also touches personal ones. |
| **Modular carries no `HouseId`** | Confirmed as the business rule 2026-08-14: modular houses ship as custom builds, so a foreign key to a catalogue row would claim what shipped matches that row. Refused server-side. `PurchaseCategories.WithGalleryModels` is the whole change if that ever stops being true. |
| **Factory delete is Restrict** | Cascade would delete a customer's purchase history because somebody removed a supplier. The panel offers **deactivate** instead, and hides Delete entirely once anything points at the row. |
| **Neither identifier is required** | A customer whose ЕИК has not come through yet is still a customer, and a form that refuses to save is a form that gets `000000000` typed into it. Checksums are enforced when a value IS present. |

### The ЕГН checksum has a country gate — do not remove it

`BulgarianIdentifiers` validates both numbers, which is worth it because a transposed digit
does not fail anywhere: it is stored, printed onto an invoice, and found by an accountant
weeks later. But **the ЕГН check runs only when the customer's country is Bulgaria or
blank.** A foreign buyer's identity number can be ten digits and will not satisfy a Bulgarian
checksum, and refusing to store a real passport number is the worse failure. Blank counts as
Bulgarian, and the error message names the fix ("set the country first").

Test vectors in `CustomerAdminTests` were generated from the published algorithms, not copied
from real people or companies. Note `1234567890` is a *valid* ЕГН by checksum — it cost a
test failure to discover, so use `1234567891` when you want an invalid one.

### Personal data — the three rules every new endpoint here must keep

1. **AdminOnly, no anonymous read path**, including for the invoice files. They go to the
   private `lead-files` container under a `customers/{id}/` prefix and are served by row id
   through an authenticated endpoint — the blob key never reaches the browser.
2. **`no-store` on every response.** A browser cache holding an ЕГН on a shared office
   machine is exactly the failure this table must not have.
3. **An ЕГН is never a lookup key.** Search matches name, phone, email and ЕИК and nothing
   else, so a personal id cannot be used to find anybody; and the LIST endpoint does not
   return `PersonalId` at all, only the detail record does. Do not add `PersonalId` to the
   search predicate — a query string outlives the response in logs and browser history, and
   that is the moment people would start typing one there.

   **What this does not claim:** the search box sends whatever was typed as `?q=`, so
   somebody *can* put an ЕГН in a URL by typing it. There is no client-side guard against
   that and there cannot usefully be one — **a Bulgarian mobile number is also ten digits**,
   so any shape-based check would break phone search. That same collision is why the ЕГН
   checksum is gated on the country rather than applied to anything ten digits long.

### One field where the lead sheet had two

"Модел от галерията" (a dropdown of catalogue models) and "Какво търси (свободен текст)"
asked the same question, so sales filled in whichever they reached first. They are now a
single combobox — `src/admin/modelPicker.js`, shared with the customer sheet.

variation note" at the same time. Opening and saving such a lead keeps the linked model and
drops the free text. `Lead.cs` still describes both being set — that was true of the old
two-field form.

## Added 2026-08-13 — tagged deploy-2026-08-13; DB migrated, app deploy still to run

**Two words that used to be one.** An *inquiry* (запитване) is the form somebody filled in
on the site; a *lead* is the person we are now talking to. The panel called the first
"Leads" and the second "Deals". Now:

| Was | Is | Route |
|---|---|---|
| Leads / Запитвания | **Inquiries / Запитвания** | `/admin/inquiries` (`/admin/leads` redirects) |
| Deals / Сделки | **Leads / Лийдове** | `/admin/pipeline`, unchanged |

The API routes did **not** move. `/api/admin/leads` is still the inquiry queue and
`/api/admin/pipeline` is still the leads board — renaming those is churn with nothing in it
for the people using the panel, so the mismatch is deliberate and commented in both
controllers.

What else shipped in the same pass:

- **The email address in the inquiry queue is a button, not a `mailto:`.** It creates the
  lead and drops you in its conversation. A mail client would have sent the reply from
  somebody's personal account, past `contact@`, and out of the thread entirely.
- **An archive for inquiries.** `Offer.ArchivedAt` / `Question.ArchivedAt`, hidden from
  every other view including "All", excluded from the nav badge, restorable, and never
  deleted. Undo after the fact rather than "are you sure?" before it.
- **Attachments both ways in the conversation.** The poller now files what customers email
  us (inline signature images skipped, same allow-list as the upload button), and a reply
  can carry files out — one request, capped at 3 MB total because that is Graph's limit for
  attaching without an upload session. Bigger files go in via "+ Note", which stores up to
  20 MB and emails nothing. **No new Graph permission**: reading attachments is covered by
  the `Mail.Read` the poller already needs.
- **The drafter can quote prices.** It now gets the linked model's description plus a
  one-line-per-model price list of the published range, so "what else do you have around
  20 000?" gets an answer instead of "a colleague will confirm". Unpublished houses are
  never quoted. Still ~2-3k tokens, still nowhere near the 20k configurator dump.
- **`Lead.NextContactAt` — the follow-up date.** A date, not a datetime: stored at
  midnight UTC (`LeadService.TryParseFollowUpDate`), so "due Tuesday" means the same day
  wherever it was saved. Editable in the lead details and on the new-lead form.
- **The Due view and its emailed report.** `/admin/pipeline?view=due` lists open leads
  whose date has arrived, most overdue first; Won/Lost never appear whatever their date
  says. "Send report" emails that list — names, one recognition line, and a link per
  lead back to the panel; *never* conversation content, because an inbox has none of the
  panel's protection. Empty recipient = the signed-in person. No email at all when
  nothing is due, so the report never becomes reflex-deleted noise. Sending is manual
  for now; a scheduled morning send would be a `BackgroundService` like LeadMailPoller,
  queued for later.
- **A full-screen reader on each lead** — the whole thread plus the standing notes,
  for catching up on a long conversation before picking it back up.

### The CRM leads are imported — 2026-08-13

The Quickbase **Lead** table `bvucxewvr` (the relationship sheet sales kept by hand, NOT
the website form tables) is now in SQL: **257 leads, 208 linked to a catalogue house, 0
unresolved links.** Re-runnable — matched on `Lead.QuickbaseRecordId`, so a second run
updates in place.

```bash
cd api-dotnet
QB_TABLE_CRM_LEADS=bvucxewvr dotnet run -- import-crm-leads --dry-run
QB_TABLE_CRM_LEADS=bvucxewvr dotnet run -- import-crm-leads
```

`QB_TABLE_CRM_LEADS` is deliberately NOT in App Service. This is a one-time move, not a
live source — once imported, the panel is authoritative and Quickbase stops being read.

Two read-only tools were added to make the mapping decisions against real data instead of
guesses, and they work on any table: `dotnet run -- qb-peek <tableId> [rows]` (fields, then
the newest records raw) and `dotnet run -- qb-values <tableId> <fid,fid,…>` (every distinct
value with counts, paged past the 500-row cap).

**Mapping decisions that cost thought — see `CrmLeadImportTests` before changing any:**

- **Quickbase has nine stages plus a separate Open/Closed flag; we have six stages where
  Won and Lost *are* closed.** Half that table is Closed while still on a mid-pipeline
  stage — leads the team gave up on, most with Lost Reason "No response". **Closed and not
  Won imports as Lost.** Leaving them Open would have dropped 100 dead leads onto the
  working board on day one. Result: 111 contacted, 100 lost, 20 won, 16 new, 7
  negotiating, 3 quoted.
- **"Чакат Оферта" is Contacted, not Quoted.** It means *they are waiting for a quote* —
  we owe them one and have not sent it.
- **A phone-only lead is still a lead.** The first cut skipped rows with no name and no
  email; four real customers were phone-only. The blank-row test is now name AND email AND
  phone.
- **Fields with no column are folded into Notes**, labelled `— от Quickbase / imported —`:
  size, budget, timeline, delivery region, preferred contact. Keeping somebody's work
  without putting five more boxes on every future lead's form.
- `-` and `Не е споменато` are placeholders for empty and import as null.

## Gotchas found the hard way — do not re-derive these

- **The two sales checkboxes are at different field ids per table.** Offers use 13/14,
  questions use **9/10**. Verified against the live tables with `dotnet run -- lead-schema`.
  Reading 13/14 for questions would have imported every question as "not contacted" and
  reset the work queue at cutover. Codified in `EnvConfig`.
- **Quickbase's query capped at 500 rows with no warning.** A longer lead history would
  have imported as "the first 500" and looked complete. `QueryPageAsync` now paginates.
- **`selectedModel` in `App.jsx` was only ever set, never cleared.** Once a visitor clicked
  "request a quote" on a gallery house it stuck for the session, so a later enquiry from
  the configurator or doors page arrived linked to a house they'd stopped looking at. Now
  cleared on navigation and modal close.
- **This dev machine's `SQL_CONNECTION_STRING` points at PRODUCTION**, not LocalDB. Anything
  run here writes to the live database. Check before running any import.
- **This dev machine has no Graph or SMTP credentials** — only Quickbase, SQL and Blob. The
  email path cannot be exercised locally at all.
- **`dist/` in the frontend is a stale August leftover.** The real build output is
  `api-dotnet/wwwroot` (`vite.config.js` → `outDir`). Don't verify a build by reading `dist/`.
- **DKIM was missing entirely** — that was the spam cause, fixed 2026-08-11. DMARC is still
  `p=quarantine`; tighten to `p=reject` once DKIM has been passing a few weeks. DNS is
  GoDaddy, mail is M365.

### Email: outbound now, inbound later

**Decided:** sales replies **from the admin panel**. The internal notification email becomes
a "go look at this" ping, not something you reply to.

The shared mailbox is **`contact@nvc-home4you.eu`** — already the address in the welcome-email
signature, so customers see one consistent sender.

**Do not set `Reply-To` to the individual salesperson.** It would send the customer's reply
straight to a personal mailbox, bypassing `contact@`, and that reply would never reach the
lead thread. Personalisation goes in the body and signature, never the headers.

Stage it: **outbound first** (useful immediately), inbound as phase 2. Going for the full
thread at once means nothing works until all of it works.

**Inbound, when we get there.** The app authenticates to Graph with client credentials and
the `.default` scope, so it uses *application* permissions and already holds `Mail.Send`.
Adding inbound needs:

1. `Mail.Read` on the same app registration + admin consent.
2. **An Application Access Policy scoping it to `contact@` only.** Application permissions
   are tenant-wide by default — without this the app can read every mailbox in the company.
   `New-ApplicationAccessPolicy` in Exchange Online PowerShell.
3. A `BackgroundService` polling every ~2 min. Simpler than Graph webhooks, which need
   subscription renewal every ~3 days plus a validation handshake. The app has no scheduler
   today.
4. Match replies by Graph's **`conversationId`** — stored on send. The payoff: mail the team
   sends straight from Outlook also lands in the thread, so nobody has to live in the admin
   panel for the history to be complete.
5. Trim quoted reply history. Sounds trivial, isn't — it's what makes homegrown threads
   unreadable.

### Also queued

- **AI-drafted replies, grounded in the catalogue.** Confirmed as the goal on 2026-08-12:

## What shipped 2026-08-11

Five commits, all live:

1. **`4200517` — the lead write no longer fails silently.** Quickbase answers `200` with
   `metadata.lineErrors` when it accepts the request but rejects the record. The old code
   called only `EnsureSuccessStatusCode()`, so a rejected lead returned
   `200 {recordId: null}` and the customer saw "thank you". `lineErrors` wasn't even
   modelled, so the reason was discarded during deserialization.

   The response is now three-way, and the middle row is the interesting one:

   | Situation | Response |
   |---|---|
   | Write landed | 200 |
   | Write failed, **sales email sent** | 200 + error log — the lead reached a human |
   | Write failed, **sales email failed** | 502 — nothing captured it anywhere |

   Both controllers previously discarded the `bool` from `TrySendLeadNotificationAsync`;
   it now decides that middle case. The frontend only reads `res.ok`, so the status code
   carries the meaning.

2. **`068448b` — `lead-schema` + `import-leads`.** See Commands below.
3. **`739a7f8` — Bulgarian internal notification to all three of sales**, and the stale
   `selectedModel` fix (below).
4. **`31f2455` — welcome email signed with the company logo and details.**
5. **`a30c5a6` — the admin leads queue** at `/admin/leads`.

## Gotchas found the hard way — do not re-derive these

- **The two sales checkboxes are at different field ids per table.** Offers use 13/14,
  questions use **9/10**. Verified against the live tables with `dotnet run -- lead-schema`.
  Reading 13/14 for questions would have imported every question as "not contacted" and
  reset the work queue at cutover. Codified in `EnvConfig`.
- **Quickbase's query capped at 500 rows with no warning.** A longer lead history would
  have imported as "the first 500" and looked complete. `QueryPageAsync` now paginates.
- **`selectedModel` in `App.jsx` was only ever set, never cleared.** Once a visitor clicked
  "request a quote" on a gallery house it stuck for the session, so a later enquiry from
  the configurator or doors page arrived linked to a house they'd stopped looking at. Now
  cleared on navigation and modal close.
- **This dev machine's `SQL_CONNECTION_STRING` points at PRODUCTION**, not LocalDB. Anything
  run here writes to the live database. Check before running any import.
- **This dev machine has no Graph or SMTP credentials** — only Quickbase, SQL and Blob. The
  email path cannot be exercised locally at all.
- **`dist/` in the frontend is a stale August leftover.** The real build output is
  `api-dotnet/wwwroot` (`vite.config.js` → `outDir`). Don't verify a build by reading `dist/`.
- **DKIM was missing entirely** — that was the spam cause, fixed 2026-08-11. DMARC is still
  `p=quarantine`; tighten to `p=reject` once DKIM has been passing a few weeks. DNS is
  GoDaddy, mail is M365.

## The Leads table — schema shipped 2026-08-12, not yet deployed

`Lead`, `LeadActivity` and `LeadService` exist, with the migration
`20260812131902_AddLeadsAndActivities`. **The migration has NOT been applied** — this dev
machine points at production, so it was generated here and deliberately not run. Applying it
is a deploy step: `dotnet ef database update`, per `DEPLOY.md`.

Still to build on top: the admin detail view (thread + status + owner), outbound email, then
the rest of the queue below.

One thing the schema now encodes that cost real time to work out — **`Offer.ModelId` is the
house's PUBLIC gallery id, not its SQL primary key.** `SqlGalleryService` serves
`QuickbaseRecordId ?? Id`, so an imported house is only ever addressed by its Quickbase id.
Resolving a model id by matching `House.Id` first — the obvious implementation — attaches the
lead to a different building, silently. `LeadService.ResolveHouseIdAsync` inverts it properly
and is covered by tests.

A lead is **not** a bigger offer: an offer is an immutable event, a lead is a relationship
with an owner, a status and a history.

### `LeadActivity` — the thread

One row per email, call, meeting or note: type, body, who, when. This is what the chat view
renders and what any future automation reads.

### Email: outbound now, inbound later

**Decided:** sales replies **from the admin panel**. The internal notification email becomes
a "go look at this" ping, not something you reply to.

The shared mailbox is **`contact@nvc-home4you.eu`** — already the address in the welcome-email
signature, so customers see one consistent sender.

**Do not set `Reply-To` to the individual salesperson.** It would send the customer's reply
straight to a personal mailbox, bypassing `contact@`, and that reply would never reach the
lead thread. Personalisation goes in the body and signature, never the headers.

Stage it: **outbound first** (useful immediately), inbound as phase 2. Going for the full
thread at once means nothing works until all of it works.

**Inbound, when we get there.** The app authenticates to Graph with client credentials and
the `.default` scope, so it uses *application* permissions and already holds `Mail.Send`.
Adding inbound needs:

1. `Mail.Read` on the same app registration + admin consent.
2. **An Application Access Policy scoping it to `contact@` only.** Application permissions
   are tenant-wide by default — without this the app can read every mailbox in the company.
   `New-ApplicationAccessPolicy` in Exchange Online PowerShell.
3. A `BackgroundService` polling every ~2 min. Simpler than Graph webhooks, which need
   subscription renewal every ~3 days plus a validation handshake. The app has no scheduler
   today.
4. Match replies by Graph's **`conversationId`** — stored on send. The payoff: mail the team
   sends straight from Outlook also lands in the thread, so nobody has to live in the admin
   panel for the history to be complete.
5. Trim quoted reply history. Sounds trivial, isn't — it's what makes homegrown threads
   unreadable.

### Also queued

- **Archive (not delete) for test offers/questions**, with an "are you sure?" confirm.
  Archived rows hidden from both reports, recoverable.
- **AI-drafted replies, grounded in the catalogue.** Confirmed as the goal on 2026-08-12:
  drafts should answer from our actual models and prices, not just from the thread.

  That is a bigger prompt than the original estimate assumed. Thread-only is ~2k tokens in;
  the generated catalogue data is 77KB across `boxConfiguratorOptions.js` (52KB) and
  `boxConfiguratorCatalog.js` (25KB), so ~20k tokens. Stuffing all of it in makes every draft
  ten times the input it needs to be, and buries the one model the customer asked about in a
  list of everything we sell — which costs answer quality before it costs money.

  Note what is NOT needed: the catalogue PDF itself. `scripts/catalogue/` already distilled
  it into those two files, so nothing downstream should ever parse the 82MB source again.

  **Send the narrow slice, not the catalogue.** The lead already carries what picks it:
  `HouseId` resolves to the exact catalogue row (title, description, price), and `CustomModel`
  plus the thread carry the free-text case. Retrieve those, not the file.

  Draft only, never auto-send. The stored `Locale` means drafts come back in the customer's
  language.
  **Billing is separate from any Claude subscription** — needs API billing at
  `console.anthropic.com` and an `ANTHROPIC_API_KEY` in App Service, which then joins the
  six-monthly renewal list. Do this after the activity log exists; draft quality depends on
  having a thread to read.

## Commands

```bash
# Read-only: dump every field on both Quickbase lead tables
cd api-dotnet && dotnet run -- lead-schema

# Import Quickbase leads into SQL. Idempotent — matched on Quickbase record id.
dotnet run -- import-leads --dry-run
dotnet run -- import-leads

# Acceptance gate — exits non-zero on any difference
dotnet run -- compare-leads
```

Re-run `import-leads` immediately before flipping `DATA_SOURCE_LEADS=sql` to sweep up
anything that arrived since. Last run: 208 offers + 44 questions, 252 compared, 0 differences.

## Flags

| Setting | Default | Effect |
|---|---|---|
| `DATA_SOURCE_LEADS` | `quickbase` | `sql` makes SQL authoritative for new leads |
| `LEADS_DUAL_WRITE` | off | `true` writes both stores, logs divergence — the soak |
| `LEAD_NOTIFY_EMAIL` | all three of sales | Overridden by App Service if set there |

Both lead flags are inert without `SQL_CONNECTION_STRING`.

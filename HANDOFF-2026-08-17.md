## Prerendering — read this before the next release

**The prerender does not run on production.** It runs locally against a local app, and the
output ships inside the publish (`StagePrerenderedForPublish` in the csproj). There is
nothing to run on the server.

**`api-dotnet/prerendered/` is gitignored, so those 55 snapshots live on one machine.**
Nothing is tracked in git; the publish stages whatever is on that machine's disk. So a
publish from a different machine, a fresh clone, or a cleaned tree ships **zero** snapshots
and quietly undoes the body-prerendering work — the site still looks perfect to a human and
serves an empty `<div id="root">` to a crawler, which is the whole problem that work fixed.

The csproj degrades on purpose rather than failing, because a client-rendered publish is a
working site. It tells you which happened, and **that line is the one to look for in the
publish output**:

- `Prerendered pages staged for publish: 55 files.` — good.
- `No prerendered pages found - the site will ship client-rendered only.` — a *warning*, easy
  to scroll past in VS Code's publish log, and the only warning you get.

**A backend-only change does not need a re-prerender.** `npm run build` content-hashes the
bundles, so with no frontend source touched the hashes are unchanged and the existing
snapshots still reference live files. §6b applies when page copy, routes or the gallery
changed. Check the count line either way.

**The route count changed on master: expect 52, not 55.** Removing the services page removed
three routes, and the three stale snapshots were deleted by hand (the prerender script
writes files, it does not prune ones whose route is gone — so a removed page's snapshot
would otherwise keep shipping and keep being served).

**The next release REQUIRES the full §6b pass — it is not optional this time.** Two reasons,
either alone would be enough:

1. Routes changed (services page removed), so the sitemap and manifest must regenerate.
2. **Frontend source changed** (the slug fix touched `galleryUtils.js`), so `npm run build`
   mints new hashed bundles and `emptyOutDir` **deletes the old ones**. The existing
   snapshots reference the old bundle filenames — shipped as-is, every prerendered route
   would load HTML whose `<script>` points at a file that no longer exists, and React would
   never boot on those pages for real visitors.

Sequence: `npm run build` → start the app with the DATA_SOURCE flags → `npm run prerender`
(expect **52/52**) → publish → restart.

```bash
cd "NVC Claude version" && npm run build
cd ../api-dotnet && DATA_SOURCE_GALLERY=sql DATA_SOURCE_CASES=sql DATA_SOURCE_REVIEWS=sql dotnet run
# second terminal:
cd "NVC Claude version" && npm run prerender     # expect 55/55
```

Five traps, every one of which produced a successful-looking run:

1. **`DATA_SOURCE_GALLERY`, not `DATA_SOURCE_HOUSES`.** EnvConfig's own comment had the wrong
   example. Without the flag a dev machine reads Quickbase while production reads SQL, so
   snapshots freeze the wrong store's prices over the correct data. The script now compares
   the local catalogue against the live site and **refuses to run on a mismatch**.
2. **Build → start → prerender, in that order.** The app reads `index.html` once at startup;
   rebuilding while it runs leaves it serving a deleted bundle and every snapshot comes out
   empty. The script refuses rather than writing 55 blank pages.
3. **The generator will read its own output.** The server serves snapshots, so it re-saved
   the previous run — identical character counts, and a fixed URL stayed broken across two
   rebuilds. It sends `X-Prerender-Bypass: 1`. **Do not remove that header.**
4. **Restart after prerendering.** Snapshots load at startup. A stale one is why the prices
   card links looked broken after they were fixed — I hit this while verifying the fix for it.
5. **The rendered DOM has two of every meta tag** (server-injected + react-helmet). Harmless
   in a request, fatal frozen. `dedupeHead()` keeps helmet's; `<title>` is exempt because
   helmet retitles the existing element rather than adding one.

## Saved configurator links — the last table off Quickbase

`SavedConfig` entity, `ISavedConfigStore` seam, `SqlSavedConfigService`,
`SavedConfigImportService`, 15 tests. Flag: `DATA_SOURCE_SAVEDCONFIGS=sql`.

**This one has a Quickbase fallback that no other migration had.** These codes are already
in customers' inboxes. Everywhere else a bad cutover showed up as a wrong page somebody
noticed; here it is a customer clicking a link *we* sent them and getting nothing, with no
signal back. So a SQL miss falls through to Quickbase — the flag can be flipped before the
import runs, and a dead Quickbase degrades to "not found" rather than a 500.

- **Code minting checks both stores.** A code that exists only in Quickbase is invisible to a
  SQL-only uniqueness check; re-minting it would point one customer's link at another's
  configuration.
- **The importer never overwrites a code already in SQL.** After cutover those are live rows
  saved natively; a stale copy landing on one breaks a link somebody holds.

The Quickbase token expires **~Feb 2027** and fails silently. This is what removes that.

## Prices page

`/bg/ceni`, `/en/prices`, `/el/times`. Two sections — 8 box houses, 6 wagons — each with
cards then its own table. Cards link to the model's catalogue page. Verified at 375px and
1280px.

**Priced from `/api/gallery`, never from a second list.** The page's own copy of the box
prices was deleted after the 73 m² incident: the gallery said €25,500 and the configurator
catalogue said €26,500 for the same house, for weeks, and nothing could notice.
`prices.js` adds only assembly costs, keyed by **gallery id** so a title edit cannot silently
drop one.

**The two sections do opposite arithmetic:**

| | Box houses | Wagons |
|---|---|---|
| Gallery price is | the house, inc VAT | the **total**, inc VAT, assembly already inside |
| Assembly | **ADDED** (€700–€3,000 net, shown ±VAT) | **SUBTRACTED OUT** (€1,000 gross) |

Treating a wagon like a box house overstates it by €1,000. Table shapes differ (5 vs 4
columns) so a reader never has to know which rule a row follows. Pinned in `prices.test.js`.

> **Two errors worth remembering.** The first version treated house prices as net and grossed
> up the sum — charging VAT twice, overstating every total by ~€2,400. And the card links
> read `row.item.href`, which is always `undefined`, so every card fell back to `to="#"` and
> clicking did nothing; the property is **`url`**. The `'#'` fallback is what hid it — a link
> that swallows the click looks interactive and is not.

## `www` — diagnosed 2026-08-17

**Root cause: `www` is not bound as a custom domain in App Service.** Everything else follows
from that one fact, and it is not a DNS problem — DNS is already correct.

```
www.nvc-home4you.eu  CNAME -> nvc-home4you.eu
nvc-home4you.eu      A     -> 13.69.68.48, 104.47.160.14
```

So requests for `www` do reach App Service, which has no such hostname and answers
**`404 Site Not Found`** on :80 (verified with a raw `Host: www.nvc-home4you.eu` request). On
:443 there is no certificate to select, SNI falls back to `*.azurewebsites.net`, and the
handshake fails before any HTTP response exists.

**Both apex A records are fine.** `104.47.160.14` sits in a Microsoft range normally used for
Exchange Online and looks alarming; it is not. Both IPs serve the same site, present the same
`CN=nvc-home4you.eu` certificate, and returned byte-identical responses (34,950 bytes, same
`ARRAffinity` value). Checked so nobody else has to.

**This is worse than a dismissible warning.** HSTS is sent with `includeSubDomains`, so any
browser that has loaded the apex in the past year force-upgrades `www` to https and then hits
the certificate mismatch — which for an HSTS host Chrome will not let the visitor click
through. For a returning visitor `www` is a hard wall, not a warning.

**The existing certificate cannot be extended.** Its SAN is exactly one name,
`DNS Name=nvc-home4you.eu` — App Service managed certificates are single-hostname, so `www`
needs its own.

### The fix, in this order

> **Domain validation and certificate eligibility are two different bars, and the second is
> stricter. This cost a round trip on 17 Aug — do not repeat it.** A `www` CNAME pointing at
> the apex plus an `asuid.www` TXT record is enough for Azure to *validate* and bind the
> hostname. It is **not** enough to issue a managed certificate, which fails with:
>
> ```
> Hostname not eligible for App Service Managed Certificates creation. Ensure that your
> domain www.nvc-home4you.eu has an active CNAME record which is set to
> nvchome4you.azurewebsites.net.
> ```
>
> For a **subdomain**, an App Service managed certificate requires a CNAME pointing directly
> at the app's own hostname. A CNAME to the apex resolves through the apex's A records, and
> A-record mappings are only eligible for the **root** domain (which cannot be a CNAME at
> all). So the apex and `www` genuinely need different DNS shapes.

1. **DNS at GoDaddy** — point `www` at the app itself, not at the apex:

   | Type | Name | Value |
   |---|---|---|
   | CNAME | `www` | `nvchome4you.azurewebsites.net` |
   | TXT | `asuid.www` | `B050EBF18CAC7088003A3DE8CA567367BAC19A1BFDC0824B4D6B596C5B6D6C26` |

   The TXT is the app's Custom Domain Verification ID, read out of the existing
   `asuid.nvc-home4you.eu` record — it is per-app, not per-hostname, so the same value is
   correct for `www`. With a direct CNAME it is not strictly required, but it costs nothing
   and keeps validation working if the CNAME is ever changed back.

   Note the app hostname has **no hyphens**: `nvchome4you.azurewebsites.net`, not
   `nvc-home4you.azurewebsites.net`.

   Pointing `www` at the apex instead is tempting — `www` then tracks the apex automatically
   if the inbound IP changes. It is also not eligible for a certificate, and the reasoning was
   weak anyway: `nvchome4you.azurewebsites.net` is a stable name that follows the app, so a
   direct CNAME needs no maintenance either.

2. **App Service → Custom domains → Add custom domain** → `www.nvc-home4you.eu`.

3. **Add an App Service Managed Certificate for `www.nvc-home4you.eu`** and bind it (SNI SSL).
   This is the step that clears the browser error.

**Order matters, and the redirect cannot substitute for the certificate.** TLS is negotiated
before HTTP exists, so until step 3 the browser never sees a redirect — shipping the code half
alone changes nothing a visitor can observe. Equally, steps 1–3 without the redirect leave two
hostnames serving identical content, which is the duplicate-content problem the SEO work just
removed. Both halves are needed.

The redirect is `Services/CanonicalHost.cs` plus ~15 lines in `Program.cs`, after the HSTS
block so the redirect carries the header too. **301 for GET/HEAD, 308 for everything else** —
a 301 permits a client to re-issue a POST as GET, which would turn a form submission on `www`
into a lead that silently never arrived. 18 tests in `CanonicalHostTests.cs`.

### The default hostname is a third live host — and it is already handled

`nvchome4you.azurewebsites.net` serves the full site (200, ~34.8KB). **Checked 2026-08-17: its
canonical tag already points at `https://nvc-home4you.eu/bg`**, so the duplicate-content
signal is correct and nothing needs doing. `robots.txt` there also points at the apex
sitemaps.

Deliberately **not** redirected by `CanonicalHost`, which only strips a `www.` label. Sending
the `*.azurewebsites.net` hostname to the apex would break the portal's Browse button,
Azure's own probes, and — most importantly — the HTTP validation path that managed certificate
issuance and renewal rely on. The canonical tag is the right tool here.

It also resolves to `104.47.160.14`, which settles the earlier question: that address is an
App Service inbound IP, not anything to do with Exchange Online.
